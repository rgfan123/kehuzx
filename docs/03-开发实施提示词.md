# 开发实施提示词

下面的提示词可直接交给开发型 AI 使用。若项目已有技术栈，以现有项目为准；若项目为空，应先给出技术选型方案并等待确认，不得擅自生成一套不可维护的临时代码。

---

你是一名负责端到端交付的高级全栈工程师。请在当前代码仓库中实现“客户、样品及订单管理系统”。

开始工作前，必须完整阅读并以以下文档为业务和工程依据：

- `docs/01-业务需求文档.md`
- `docs/02-开发指导.md`

如果代码仓库中存在 `AGENTS.md`、README、现有架构规范、数据库迁移规则、设计系统或测试约定，也必须先阅读并遵守。现有项目约定与业务文档不冲突时，优先沿用现有项目模式，不要引入重复框架或无必要依赖。

## 工作目标

实现以下一级模块及页面：

1. 客户：客户列表、客户详情、客户需求、当前客户的样品模板、样品订单和正式订单。
2. 样品：样品模板、样品订单、样品订单流程。
3. 正式订单：正式订单列表、正式订单流程。
4. 供应商：供应商档案列表和基础增删改查。

核心业务链路为：

```text
客户 -> 多条客户需求 -> 单产品样品模板
-> 多模板组成样品订单 -> 样品流程
-> 已确认模板组成正式订单 -> 正式订单流程
```

## 不可违反的业务规则

1. 一个客户可以有多个需求，一条需求描述一个产品方向。
2. 一个样品模板只对应一个产品，模板状态必填且默认“草稿”。
3. 产品品类、肉类等级、货品状态当前使用普通文本输入，不做固定选项。
4. 一张样品订单或正式订单包含多个产品，必须采用订单主表和订单产品明细结构。
5. 交付信息和结账信息属于订单主表，由整张订单内的产品共用。
6. 供应商关联到订单产品明细，可为空；为空表示由本公司供应。不要把唯一供应商强制放在订单主表。
7. 模板加入订单时必须复制产品基础信息、产品规格和单份供价形成订单快照。以后修改模板不得改变历史订单。
8. 数据库内部 ID 和业务编号分开；内部 ID 由系统生成，业务编号系统自动生成且唯一。
9. 空内容在数据库中保存为 `NULL`，界面显示“无”，不能把“无”写入数字、日期、布尔或外键字段。
10. 所有列表默认每页 5 条，采用服务端搜索、筛选、排序和分页。
11. 草稿订单不进入流程；订单提交后才进入第一个流程状态。
12. 流程只能按预设顺序推进，最终状态不能继续推进。
13. 中止是独立状态，不得混入流程枚举。中止必须填写原因；已中止订单不能推进；取消中止后恢复原流程状态。
14. 所有流程变化必须记录原状态、新状态、操作人、操作时间和备注。
15. 客户、模板、订单等业务对象使用软删除，不能通过级联物理删除破坏历史数据。

## 实施方式

第一步先检查仓库，汇报：

- 当前技术栈和目录结构
- 已有功能与可复用模式
- 数据库与迁移机制
- 测试、格式化、类型检查和构建命令
- 与需求冲突或仍需确认的事项

如果仓库为空，只提交一份简洁、可执行的技术选型和项目结构方案，明确前端、后端、数据库、认证、测试和部署方式，等待确认后再编码。

如果仓库已有可用技术栈，则直接制定分阶段实施计划并执行。不要只给建议，也不要一次性堆出未经验证的大量代码。按以下顺序交付：

1. 基础数据模型、数据库迁移、统一分页和错误结构。
2. 客户档案、客户需求、客户详情。
3. 样品模板及模板复制。
4. 供应商档案。
5. 样品订单主表、产品明细、快照、草稿和提交。
6. 样品订单流程、中止、恢复和流程日志。
7. 正式订单及其流程。
8. 搜索、审计、权限、测试和响应式体验完善。

每完成一个阶段，都必须：

- 执行数据库迁移或迁移检查。
- 运行相关单元测试和集成测试。
- 运行类型检查、格式检查和构建。
- 说明已完成内容、验证结果和剩余工作。
- 修复由本阶段引入的失败后再继续。

## 后端要求

- 使用明确的数据模型和外键，不把多个产品保存为不可查询的大段文本。
- 金额和数量使用定点小数，不使用浮点数。
- 状态推进、中止、恢复、快照复制和日志写入必须由后端事务处理。
- 下一状态由后端根据当前状态计算，客户端不得任意指定目标状态。
- 使用乐观锁、版本字段或条件更新避免重复推进流程。
- 所有写接口实施服务端校验、权限检查和一致的错误返回。
- 搜索接口支持客户、编号/名称、产品、创建时间、交付时间和状态等需求文档规定的条件。

## 前端要求

- 使用现有设计系统和图标库；没有时选用成熟、克制的后台管理界面方案。
- 一级导航明确区分客户、样品、正式订单和供应商。
- 客户列表采用条状展示，客户详情顶部展示基础信息，下方使用标签页或嵌套路由展示需求、模板、样品订单和正式订单。
- 样品和正式订单流程页面复用同一类流程列表组件，通过状态参数筛选，不复制多套页面逻辑。
- 订单编辑器清楚区分整单信息与多条产品明细。
- 保存草稿和提交订单使用不同操作。
- 删除、推进流程、中止、恢复必须二次确认；中止使用弹窗收集中止原因。
- 提供加载、空数据、错误、无权限和提交中状态，防止重复操作。
- 所有字段在常见桌面和移动视口中不得溢出、遮挡或引起不合理布局跳动。

## 测试和验收

至少实现并验证以下完整场景：

```text
创建客户
-> 新增两个客户需求
-> 分别创建两个样品模板，确认默认状态为草稿
-> 将两个模板加入同一张样品订单
-> 为两个产品选择不同供应商，其中一个也可不选供应商
-> 填写数量、交付和结账信息
-> 保存草稿并提交
-> 按顺序推进流程
-> 填写原因后中止，确认无法推进
-> 取消中止并恢复原状态
-> 推进到成品确定
-> 使用模板创建正式订单并完成正式订单流程
```

同时验证：

- 模板修改不会改变历史订单快照。
- 默认每页为 5 条，搜索和翻页结果正确。
- 金额、数量、日期和空值处理正确。
- 最终流程状态不能继续推进。
- 重复点击不会造成重复订单或状态跳级。
- 软删除不会破坏历史关联。

## 工作边界

- 不修改与本需求无关的代码。
- 不擅自改变已确认字段、状态名称或业务关系。
- 遇到文档中“待产品最终确认”的事项，如果会影响数据库结构或核心交互，先列出问题和推荐方案，等待确认；不影响主体开发的事项可以采用最保守、可回滚的实现并明确记录假设。
- 不在未验证的情况下宣称完成。
- 最终交付时提供变更摘要、数据库变更、主要接口/页面、测试结果、运行方式以及仍存在的风险或待确认事项。
