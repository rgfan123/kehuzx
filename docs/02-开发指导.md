# 客户、样品及订单管理系统开发指导

## 1. 开发原则

1. 先确认现有技术栈和项目约定；若项目为空，再确定前端、后端、数据库和部署方案。
2. 需求文档是业务依据，不能因界面实现方便而改变订单、产品明细或流程含义。
3. 订单必须使用“订单主表 + 产品明细表”，不能把多个产品序列化后塞入一个不可查询的文本字段。
4. 订单产品必须保存模板快照，不能只实时读取模板。
5. 空值在数据库中使用 `NULL`，仅由展示层转换成“无”。
6. 所有流程变更、订单中止和恢复均在后端事务中完成。
7. 优先复用列表、表单、详情和流程组件，避免为每个流程状态复制一套代码。

## 2. 推荐系统分层

```text
前端页面
  -> API 客户端
  -> 控制器/路由层
  -> 应用服务层（业务用例、事务、状态流转）
  -> 领域/数据访问层
  -> 关系型数据库
```

技术栈尚未确定时，可采用成熟的前后端分离方案。无论选用何种框架，都应满足：类型明确、数据库迁移可追踪、接口可测试、表单和服务端双重校验。

## 3. 推荐数据表

### 3.1 核心表

- `customers`：客户档案
- `customer_demands`：客户需求
- `sample_templates`：样品模板及单产品字段
- `sample_orders`：样品订单主表
- `sample_order_items`：样品订单产品明细
- `formal_orders`：正式订单主表
- `formal_order_items`：正式订单产品明细
- `suppliers`：供应商档案
- `order_workflow_logs`：订单流程记录
- `operation_logs`：关键操作审计记录，可按技术栈选做独立表

### 3.2 关系约束

```text
customers 1 --- n customer_demands
customers 1 --- n sample_templates
customers 1 --- n sample_orders
customers 1 --- n formal_orders

customer_demands 1 --- n sample_templates（模板可不关联来源需求）
sample_orders 1 --- n sample_order_items
formal_orders 1 --- n formal_order_items
sample_templates 1 --- n order_items（来源引用，可为空）
suppliers 1 --- n order_items（可为空）
```

外键删除策略优先使用限制删除或软删除，不使用级联物理删除业务历史。

### 3.3 ID、业务编号与时间

- 主键可使用 UUID、ULID 或数据库自增 ID，项目内保持统一。
- 业务编号必须有唯一索引。
- 客户名称、模板名称、订单名称不强制唯一。
- 所有表至少包含 `created_at`、`updated_at`。
- 需要软删除的表增加 `deleted_at` 或 `is_deleted`。
- 时间统一按数据库时区规范保存，API 使用 ISO 8601，界面按 Asia/Hong_Kong 展示。

## 4. 字段建模建议

### 4.1 复合字段

产品基础信息、产品规格、供价和数量在多个对象中复用。实现方式有两种：

1. 使用数据库独立列：便于筛选、排序和统计，优先推荐。
2. 使用数据库 JSON：适合字段变化频繁，但搜索、校验和索引更复杂。

当前字段已相对明确，建议使用独立列，并在代码层使用可复用的数据结构、表单分组和映射函数。

### 4.2 金额与数量

- 金额使用定点小数类型，不使用浮点数。
- 数量使用可配置精度的定点小数。
- 税率明确存储单位，例如存储百分比数值 `13.00`，全系统保持一致。
- 总体数量在服务端重新计算，不能只相信前端结果。
- 若允许人工覆盖计算值，应增加覆盖标记和调整原因。

### 4.3 快照

从模板加入订单时，将以下字段复制到订单明细：

- 产品基础信息全部字段
- 产品规格全部字段
- 单份供价全部字段
- `source_template_id`
- 可选的模板编号快照

修改订单明细不会反向修改模板，修改模板也不会反向修改订单。

## 5. 状态设计

### 5.1 模板状态

代码值建议保持稳定，显示文案可以调整：

```text
DRAFT                草稿
AVAILABLE_FOR_SAMPLE 可用于样品
SUPPLIED             已被供应
DISCONTINUED         停止供应
```

默认值为 `DRAFT`。

### 5.2 样品订单流程

```text
SAMPLE_COMMUNICATION
FACTORY_COMMUNICATION
SAMPLE_PRODUCING
SAMPLE_COMPLETED
SAMPLE_DELIVERY
PRODUCT_CONFIRMED
```

### 5.3 正式订单流程

```text
ORDER_COMMUNICATION
FACTORY_COMMUNICATION
ORDER_PRODUCING
ORDER_COMPLETED
DELIVERED_TO_CUSTOMER
```

### 5.4 草稿和中止

建议将“是否已提交”和“是否中止”与流程状态分开：

- 草稿订单尚未进入流程。
- 提交后设置第一个流程状态。
- `is_suspended` 表示中止，不把“已中止”混入流程枚举。
- 记录 `suspended_reason`、`suspended_at` 和 `status_before_suspension`。

状态流转必须由后端状态机或显式映射控制，例如：

```text
SAMPLE_COMMUNICATION -> FACTORY_COMMUNICATION
FACTORY_COMMUNICATION -> SAMPLE_PRODUCING
```

禁止由客户端任意传入目标状态并直接保存。

## 6. 事务与并发

以下操作必须使用数据库事务：

- 从需求创建模板。
- 从一个或多个模板创建/更新订单草稿。
- 提交订单。
- 进入下一流程并写入流程日志。
- 中止、取消中止并写入日志。
- 从样品订单生成正式订单。

进入下一流程时应使用乐观锁、版本号或带当前状态条件的更新，避免两个使用者同时点击造成跳过状态。

## 7. API 设计建议

接口命名应遵循项目已有风格。可参考：

```text
GET    /api/customers
POST   /api/customers
GET    /api/customers/{id}
PUT    /api/customers/{id}
DELETE /api/customers/{id}

GET    /api/customers/{id}/demands
POST   /api/customers/{id}/demands

GET    /api/sample-templates
POST   /api/sample-templates
POST   /api/sample-templates/{id}/duplicate

GET    /api/sample-orders
POST   /api/sample-orders
POST   /api/sample-orders/{id}/items/from-template
POST   /api/sample-orders/{id}/submit
POST   /api/sample-orders/{id}/advance
POST   /api/sample-orders/{id}/suspend
POST   /api/sample-orders/{id}/resume

GET    /api/formal-orders
POST   /api/formal-orders
POST   /api/formal-orders/{id}/advance
POST   /api/formal-orders/{id}/suspend
POST   /api/formal-orders/{id}/resume

GET    /api/suppliers
POST   /api/suppliers
```

列表接口统一接受：

- `page`，从 1 开始
- `pageSize`，默认 5
- `keyword` 或明确字段筛选
- `createdFrom`、`createdTo`
- `deliveryFrom`、`deliveryTo`
- `customerId`
- `status`
- `sort`

统一返回：

```json
{
  "items": [],
  "page": 1,
  "pageSize": 5,
  "total": 0
}
```

## 8. 前端实现建议

### 8.1 路由

```text
/customers
/customers/:id
/customers/:id/demands
/customers/:id/sample-templates
/customers/:id/sample-orders
/customers/:id/formal-orders

/samples/templates
/samples/orders
/samples/workflow/:status?

/orders
/orders/workflow/:status?

/suppliers
```

客户详情的四个标签页可使用嵌套路由，支持刷新后保持当前标签，并允许分享具体页面地址。

### 8.2 可复用组件

- 通用搜索栏
- 服务端分页器
- 条状数据列表
- 客户选择器
- 供应商选择器
- 产品基础信息表单
- 产品规格表单
- 供价表单
- 数量表单
- 交付信息表单
- 结账信息表单
- 订单产品明细编辑器
- 订单状态标签和流程导航
- 中止原因弹窗
- 删除确认弹窗

### 8.3 订单编辑体验

- 订单基础信息和整单交付/结账信息放在主表单。
- 产品使用稳定的明细列表或分区编辑，不把多产品挤在单个横向表格中。
- 支持继续添加模板、删除明细和修改数量。
- 保存草稿和提交订单使用不同按钮。
- 提交失败时保留用户已经填写的内容并定位错误字段。

## 9. 权限与安全

即使第一阶段不建设复杂角色体系，也应预留当前用户信息，并保证：

- 后端校验所有新增、修改、删除和状态流转。
- 参数化查询，防止注入。
- 输出文本正确转义，防止脚本注入。
- 日志不记录敏感凭证。
- 删除、流程推进、中止和恢复记录操作人。

## 10. 测试策略

### 10.1 单元测试

- 业务编号生成和唯一性
- 总体数量计算
- 金额精度
- 模板默认状态为草稿
- 样品订单和正式订单下一状态计算
- 最终状态不能继续推进
- 已中止订单不能推进
- 取消中止恢复原状态

### 10.2 集成测试

- 客户及需求增删改查
- 从需求创建模板
- 从多个模板组成一张订单
- 模板修改不影响订单快照
- 产品明细按需关联不同供应商
- 提交订单的完整性校验
- 状态流转和日志在同一事务中完成
- 软删除后默认列表不可见、历史关联仍存在

### 10.3 端到端测试

至少覆盖完整主流程：

```text
创建客户 -> 新增两个需求 -> 创建两个模板
-> 组成一张样品订单 -> 提交 -> 逐级流转
-> 中止 -> 恢复 -> 成品确定
-> 使用模板组成正式订单 -> 提交并流转
```

还需验证搜索、默认每页 5 条、翻页、空数据、接口失败、重复点击和移动端布局。

## 11. 推荐开发顺序

1. 项目基础设施、数据库迁移、统一错误和分页格式。
2. 客户档案、客户需求及客户详情入口。
3. 样品模板、复用产品字段组件、模板状态。
4. 供应商基础档案。
5. 样品订单主表、产品明细、模板快照和草稿。
6. 样品订单提交、流程、中止、恢复和日志。
7. 正式订单及正式订单流程。
8. 全局搜索、审计、权限、端到端测试和体验完善。

每一阶段都应完成数据库迁移、后端接口、前端页面、自动化测试和基本文档后再进入下一阶段。

## 12. 完成定义

一个功能只有同时满足以下条件才算完成：

- 前后端行为符合业务需求文档。
- 数据库迁移可重复执行。
- 输入校验和错误提示完整。
- 关键业务规则有自动化测试。
- 列表有加载、空、错误和分页状态。
- 关键操作有确认、结果反馈和日志。
- 桌面及移动视口不存在文字溢出或控件遮挡。
- 代码通过项目已有的格式、类型检查、测试和构建命令。
